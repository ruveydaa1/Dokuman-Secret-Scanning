# 4. Secret Sızıntısı ve Müdahale Süreci

### 4.1. Secret Silinse Bile Neden Git Geçmişinde Kalır?

Git, yazılım projelerinde yapılan değişiklikleri commit adı verilen kayıtlar aracılığıyla saklar.

Bir dosyadan secret bilgisinin silinmesi, geçmiş commit kayıtlarının da otomatik olarak değiştiği anlamına gelmez.

Örneğin aşağıdaki durum gerçekleşmiş olsun:

1. Geliştirici kaynak koda bir API key ekler.
2. Dosyayı commit ederek Git deposuna gönderir.
3. Daha sonra API key'in yanlışlıkla eklendiğini fark eder.
4. Kaynak koddan bu bilgiyi siler.
5. Yeni bir commit oluşturarak değişikliği Git deposuna gönderir.

Bu durumda güncel dosyada API key bulunmaz. Ancak ilk commit içerisinde aynı değer hâlâ yer alabilir.

Bunun nedeni Git'in her commit ile ilgili dosyaların o andaki durumunu geçmişte saklamasıdır. Sonraki commit'te yapılan silme işlemi önceki commit'i değiştirmez.

Bu nedenle bir secret'ın yalnızca güncel dosyadan silinmesi yeterli değildir.

### 4.2. Git Geçmişinin Temizlenmesi

Secret'ın geçmiş commit'lerden kaldırılması için Git geçmişinin yeniden yazılması gerekebilir.

Bu işlemde kullanılabilecek araçlardan biri `git-filter-repo` aracıdır.

Araç, belirli dosyaları veya içerikleri geçmiş commit'lerden temizlemek amacıyla kullanılabilir.

Ancak geçmişin yeniden yazılması bazı sonuçlar doğurur:

* Commit kimlikleri değişebilir.
* Branch ve tag referanslarının güncellenmesi gerekebilir.
* Ekip üyelerinin yerel depolarını yeniden senkronize etmesi gerekebilir.
* Fork ve diğer kopyalar eski geçmişi tutmaya devam edebilir.
* Pull request kayıtları ve CI/CD çıktıları ayrıca kontrol edilmelidir.

Bu nedenle Git geçmişini temizlemek yalnızca bir komut çalıştırmaktan ibaret değildir. Ekip üyelerinin koordinasyonunu gerektiren bir işlemdir.

Ayrıca Git geçmişinin temizlenmesi, secret'ın daha önce kopyalanmış olma ihtimalini ortadan kaldırmaz. Bu yüzden geçmiş temizliği, anahtarın iptal edilmesinin yerine geçmez.

### 4.3. Secret Sızıntısında Müdahale Süreci

Bir secret'ın açığa çıktığı tespit edildiğinde hızlı ve planlı hareket edilmelidir.

Temel olarak üç işlem öne çıkar:

* Revoke
* Rotate
* History Cleanup

Bunların ardından kontrol ve yeniden tarama yapılmalıdır.

### 4.4. Revoke – Secret'ın İptal Edilmesi

Revoke, açığa çıkan secret'ın kullanımının iptal edilmesidir.

Örneğin Git deposunda bir API key bulunduğunda, bu anahtarı oluşturan servis üzerinden anahtar devre dışı bırakılmalıdır.

Böylece anahtarı ele geçiren kişilerin bu bilgiyle sisteme erişmeye devam etmesi engellenir.

Bu işlem neden ilk sıradadır?

Çünkü Git geçmişinde bulunan secret, dosyadan silinmiş olsa bile kullanılabilir durumda olabilir. Saldırganın bu bilgiyi kullanmasını engellemek için öncelikle erişimin kesilmesi gerekir.

### 4.5. Rotate – Yeni Secret Oluşturulması

Rotate, eski secret'ın yerine yeni bir secret oluşturulması ve sistemlerin yeni bilgiye geçirilmesidir.

Örneğin:

1. Yeni API key oluşturulur.
2. Bu anahtarı kullanan uygulamaların yapılandırmaları güncellenir.
3. Uygulamaların yeni anahtarla çalıştığı kontrol edilir.
4. Eski anahtarın kullanımı iptal edilir.

Bazı servislerde yeni anahtar oluşturup uygulamaları güncelledikten sonra eski anahtarı iptal etmek kesintiyi önleyebilir. Ancak güvenlik riski yüksekse eski anahtarın mümkün olan en kısa sürede devre dışı bırakılması gerekir.

Rotate işleminin amacı yalnızca yeni bir anahtar üretmek değildir. Bu anahtarı kullanan tüm sistemlerin de güncellenmesi gerekir.

### 4.6. History Cleanup – Git Geçmişinin Temizlenmesi

Secret'ın eski commit'lerde bulunması nedeniyle Git geçmişi temizlenmelidir.

Bu işlem için `git-filter-repo` gibi araçlar kullanılabilir.

Geçmiş temizlenirken:

* Secret'ın bulunduğu commit'ler belirlenir.
* İlgili içerikler geçmişten temizlenir.
* Güncellenen geçmiş uzak depoya gönderilir.
* Ekip üyeleri bilgilendirilir.
* Fork, branch ve tag gibi diğer kopyalar kontrol edilir.

Geçmiş temizliğinin revoke ve rotate işlemlerinden sonra yapılmasının nedeni, eski secret'ın artık kullanılamaz hâle getirilmiş olmasıdır.

Çünkü Git geçmişini temizlemek, bir saldırganın daha önce kopyaladığı anahtarı geçersiz yapmaz.

### 4.7. Son Kontroller ve Yeniden Tarama

Müdahale işlemlerinden sonra yalnızca ana dosyanın kontrol edilmesi yeterli değildir.

Aşağıdaki alanlar da incelenmelidir:

* Diğer branch ve tag'ler.
* Fork edilmiş depolar.
* Pull request kayıtları.
* CI/CD logları ve build çıktıları.
* Uygulama yapılandırmaları.
* Secret'ın kullanıldığı servisler.
* İlgili erişim ve işlem kayıtları.

Son olarak Gitleaks veya TruffleHog ile yeniden tarama yapılmalıdır.

Bu taramanın amacı secret'ın erişilebilir depo geçmişinden temizlendiğini kontrol etmek ve başka gizli bilgilerin de açığa çıkıp çıkmadığını belirlemektir.

### 4.8. Müdahale Sırasının Özeti

| Sıra | İşlem                     | Amaç                                                                 |
| ---- | ------------------------- | -------------------------------------------------------------------- |
| 1    | Revoke                    | Sızdırılan anahtarın kullanılmasını engellemek                       |
| 2    | Rotate                    | Yeni anahtar oluşturmak ve uygulamaları güncellemek                  |
| 3    | History Cleanup           | Secret'ı Git geçmişinden temizlemek                                  |
| 4    | Kontrol ve yeniden tarama | Diğer kopyaları kontrol etmek ve sızıntının giderildiğini doğrulamak |

Önemli: Sistem kesintisini önlemek için bazı durumlarda yeni secret önce oluşturulup uygulamalara tanıtılabilir ve ardından eski secret iptal edilebilir. Ancak bu süreçte sızdırılmış anahtarın kullanılabilir kalma süresi mümkün olduğunca kısa tutulmalıdır.
